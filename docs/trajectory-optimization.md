# Multi-agent trajectory optimization

> 目标驱动 KL 自动规划、数据画像、能力注册表和历史可靠性排序见
> [autonomous-kl-planning.md](autonomous-kl-planning.md)。自动规划产生的候选与选择结果会进入统一轨迹，并使用数据集指纹关联后续任务评估。

This layer turns execution history into versioned, comparable evidence. It is
research-workflow infrastructure; it does not authorize autonomous diagnosis or
patient-specific clinical decisions.

## Data flow

```text
route / plan / agent / tool events
              |
              v
       trajectory_events
              |
       pipeline_trials
              |
        artifact_registry
              |
       evaluation_results
              |
    offline policy comparison
              |
       shadow validation
              |
       human promotion gate
```

Legacy tables remain available. The normalized tables are:

- `trajectory_events`: append-only, sanitized decisions and outcomes;
- `pipeline_trials`: every attempted pipeline candidate, including failures,
  with an atomic config hash, training-only metrics, uncertainty, feature
  stability, recommended parameters, and latency;
- `artifact_registry`: content-addressed manifests and their lineage;
- `evaluation_results`: versioned metrics and hard gates;
- `policy_versions`: draft, shadow, active, retired, and rolled-back policies;
- `routing_feedback`: independent routing labels from humans, rules, or adjudication.

The active policy identifier is read from `MULTI_AGENT_POLICY_ID` and defaults
to `baseline-v1`.

## Single account, isolated learning scopes

Multiple login accounts are not required for personal self-optimization. Each
task and normalized trajectory now records four independent scope dimensions:

- `user_id`: the authenticated owner;
- `workspace_id`: a logical tenant/profile under that account;
- `agent_version`: the deployed Agent bundle from `MULTI_AGENT_VERSION`;
- `data_partition`: `train`, `validation`, or `test`.

When no workspace is supplied, the application derives a stable personal
workspace from the database user ID. API callers can pass a different
`workspace_id` to `OAI_ChatBot` to isolate projects or roles without creating
another login.

The data partition is deterministically assigned from `task_fingerprint` with
an 80/10/10 split. Retries of the same task context therefore remain in the
same partition. The offline optimizer is tenant- and version-scoped and can
learn policy candidates only from `train`; validation and test trajectories
remain unavailable to candidate generation.

## Automatic ingestion for new classifications

Successful `koa_lasso_classification` and `koa_filter_classification` calls
now trigger ETL automatically. The hook accepts only a structured tool result
with `status=success`, verifies that the returned output directory is the
requested directory or one of its descendants, and scans only that one run.
It then upserts `experiment_results`, `artifact_registry`, and
`evaluation_results`, and records an `evaluation_ingestion_completed` event.

ETL failure does not delete or hide the classification output. It is recorded
as a failed ingestion event so the result can be inspected and backfilled.
`routing_feedback` is intentionally not generated by ETL because it must come
from an independent human, rule, or adjudication label.

## Automatic task-level evaluation

Every completed or failed Agent run now passes through a deterministic
`task-contract-evaluator`. It evaluates observed Agent steps, tool calls,
current-run artifacts, terminal status, and final output rather than asking an
LLM whether the task succeeded.

The evaluator writes five metrics:

- `task_success`;
- `step_success_ratio`;
- `required_tool_coverage`;
- `false_completion`;
- `cross_run_artifact_violation`.

It also writes eight hard gates covering runtime/status consistency, required
Agent order, required tools, artifact run/type scope, train/test completeness,
downstream blocking after failure, false completion, and report ordering after
the current classification. Evaluation identifiers are deterministic for the
same trace and evaluator version, so writes are idempotent.

The task evaluator currently records evidence and exposes it in the API result;
it does not self-modify or automatically promote a production policy.

## Scientific trajectory graph artifact

Every terminal task, whether successful or requiring review, now produces three
adjacent artifacts under
`output/scientific_trajectory_graphs/<workspace_id>/<trace_id>/` by default:

- `scientific_trajectory.png`: a compact vertical graph displayed first in the
  right-hand result gallery;
- `scientific_trajectory.md`: a structured evidence report displayed beside the
  graph in the right-hand panel;
- `scientific_trajectory.json`: the versioned machine-readable graph used for
  later replay, attribution, and experience extraction.

Schema v2 records the data split and distributions, structured planning basis,
candidate metrics and uncertainty, Agent/tool timing, artifact lineage,
deterministic gate evidence, failure boundaries, reproducibility fields, and a
non-authoritative learning candidate. Missing model, prompt, tool, code,
environment, and random-seed versions are stated as unavailable instead of
being inferred. A successful run may only create an experience candidate; it is
never automatically written into long-term memory without cross-task validation
and human review.

All three artifacts deliberately exclude raw prompts, tool arguments, patient
identifiers, artifact filenames, and filesystem paths. They are registered in
`artifact_registry`; the PNG and Markdown report point to the JSON manifest as
their source artifact, and `artifact_registered` events preserve the audit
trail. A rendering or registration error is non-authoritative and never changes
the scientific task result.

Set `SCIENTIFIC_TRAJECTORY_DIR` to move the persistent root. The generated
directory is runtime data and is ignored by Git.

The initial development catalog is
`src/evaluation/task_catalog.v1.json`. It contains 20 normal and injected-failure
scenarios and is deliberately marked `draft`; independent human review and a
cryptographic freeze are still required before it can be used as a promotion
gate. Validate and summarize it from `src` with:

```powershell
python -m db_utils.task_catalog
```

Read-only comparison queries `TASK_POLICY_SCORECARD` and
`TASK_HARD_GATE_FAILURES` aggregate the new task-level records by policy, task
type, and method.

## Backfill historical experiments

From the repository's `src` directory:

```powershell
Set-Location src
python -m db_utils.experiment_etl --root task_results_history
```

Generate a scoped draft preview for an existing user (still never activates a
policy):

```powershell
python -m db_utils.offline_optimizer --username researcher --register-draft
```

Use `--workspace-id` and `--agent-version` when targeting a non-default logical
workspace or a historical Agent deployment.

LASSO JSON manifests produce content-addressed artifacts, seven classification
metrics, and three gates. Filter text summaries are normalized too, but their
missing provenance and patient-level evidence are explicitly recorded as failed
gates rather than inferred as valid.

The command above is for historical data or recovery; normal new
classifications do not require manual ETL. Imports are idempotent: artifact and
evaluation identifiers are derived from
content, method, data, policy, split, and evaluator version.

## Add routing reference labels

Execution of the routed Agent is not ground truth. Store a separate label:

```python
from db_utils.db_utils import DatabaseManager

db = DatabaseManager()
db.save_routing_feedback(
    trace_id="<trace UUID>",
    expected_agent="CLASSIFICATION_AGENT",
    observed_agent="ORCHESTRATOR_AGENT",
    label_source="human",  # or rule / adjudicated
    reviewer_id="reviewer-pseudonym",
)
db.close()
```

`routing_accuracy()` uses these reference labels. The old routed-versus-executed
comparison is retained as `routing_execution_consistency()` and must not be
reported as accuracy.

## Compare policies

Use the read-only queries in `db_utils.analysis_queries`:

- `policy_evaluation_leaderboard`: mean, SD, range, and run count by policy,
  task, method, split, and metric;
- `policy_hard_gate_summary`: pass/fail/unknown gate distribution;
- `STRICT_PROMOTION_CANDIDATES`: excludes a policy-method combination if any
  required gate is not `pass`.

Historical runs currently have `test_is_frozen=unknown`. Registering and
cryptographically freezing evaluation sets is therefore required before any
automatic policy promotion is enabled.

## Promotion rule

Agents may propose candidate configurations, but activation remains a
deterministic control-plane action with accountable human approval:

1. register the candidate as `draft`;
2. replay it on the frozen development evaluation set;
3. run it in `shadow` mode;
4. compare paired tasks, uncertainty, failures, cost, and latency;
5. require every hard gate to pass;
6. approve and activate the exact config hash;
7. retain the previous policy for rollback.

Never tune thresholds or select pipelines on the final test set.

## Task and artifact isolation

Conversation memory and executable artifacts have different scopes:

- LangGraph uses `session_id` as the conversation thread and a unique
  per-request `checkpoint_ns` as the execution namespace.
- Every request receives a fresh `run_id/trace_id` and a deterministic
  `TaskSpec` derived from the current user input.
- Explicit requests such as `extract MEAS -> LASSO` are forced through the
  orchestrator, and the plan validator inserts/reorders the required feature
  extraction step even when the LLM planner omits it.
- Classification accepts current-run feature artifacts only when fresh
  extraction was requested. It validates run ID, feature type, train/test
  role, and path before invoking a classification tool.
- Historical artifact reuse is denied by default. It is enabled only by an
  explicit reference such as "使用刚才提取的特征"; merely having paths in chat
  history does not authorize reuse.

These rules are enforced in code. Prompt instructions remain advisory and are
not the correctness boundary.

## Daily task learning loop V1

Every request now receives one task row before routing. The root control plane
owns the terminal transition:

```text
running -> deterministic task evaluation -> completed | failed
```

An Agent may update progress and error evidence, but `DatabaseManager` rejects
`status=completed` unless `completion_gate_status=pass` is supplied. The task
row stores:

- `task_fingerprint`: goal, target/label policy, dataset hashes and schemas;
- `execution_fingerprint`: task fingerprint plus policy and selected method;
- `outcome_status` and `outcome_summary_json`;
- `completion_gate_status`.

`task_fingerprint` intentionally excludes the selected method. This allows
MEAS/LASSO, LDSE/LASSO, and other methods to be compared only inside the same
decision context. Online history loading now uses this matched fingerprint and
does not transfer task-success rates across unrelated datasets.

Deterministic completion creates `rule` feedback in `task_feedback`. The chat
UI provides `correct`, `partial`, and `incorrect` buttons that create a
separate `human` feedback row. Human and rule labels are never merged into one
source. A rule-derived routing label is written only when the current-request
task specification has an unambiguous expected entry Agent; a human or
adjudicated routing label has precedence over a later rule upsert.

Candidate generation is now recorded as a successful event when the candidate
set has been generated. Trial and final selection use separate events, so a
completed selection no longer leaves `pipeline_candidates_generated=pending`.

Candidate-level learning no longer depends on accumulating 20 identical
task-level executions before any useful comparison exists. Within one KL task,
budgeted candidates form a paired comparison on the same training snapshot.
These rows may influence later portfolio priors for the exact same
`task_fingerprint`; they cannot activate a policy, alter hard gates, or use the
held-out test set. The offline preview exposes them as
`paired_trial_recommendations` with `use_mode=portfolio_prior_only`.

### Offline preview

Generate a privacy-minimizing daily preview from `src`:

```powershell
python -m db_utils.offline_optimizer `
  --output task_results_history/offline_optimizer/latest_policy_preview.json
```

The default command writes a local preview only. It never activates a policy.
To register the exact preview and its content-addressed artifact as a `draft`:

```powershell
python -m db_utils.offline_optimizer `
  --output task_results_history/offline_optimizer/latest_policy_preview.json `
  --register-draft
```

Even with `--register-draft`, `production_activation_allowed` remains false.
The candidate needs at least two safe comparable methods with the configured
minimum matched runs, followed by paired replay, shadow validation, and human
approval. Sparse, hard-gate-failing, false-completion, or cross-run-artifact
history cannot produce a preferred method.
